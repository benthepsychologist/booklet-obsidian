# Proposals for the next version of the format, from lane E1 of plugin 1.0.0

Two places where the Obsidian plugin now does something the format (`SPEC.md`) is silent on or the reference renderer does not do. Each is a one-paragraph note for the list of spec proposals.

**C-033, a structure line in a comment, a `<pre>` block or a `$$` block.** The plugin reads a Booklet line of any kind (`> [!page`, `> [!tab`, `> [!activity`, `> [!module`, a question, a row, a notice and the rest) at the start of a line inside an HTML comment, a `<pre>` block or a `$$` block as plain text: it starts nothing, so a page, tab, activity or question that has been commented out does not appear (a footnote definition and a heading as a link target are treated the same way). A region hides lines only when its closer is found later in the note; an opener with no closer hides nothing (a closer is looked for only in the body, outside fenced code and before the records section). Proposed for the spec: say that a structure line is read only where a reader sees it, never inside an HTML comment, a `<pre>` block or a `$$` block, and that an opener with no closer hides nothing; and settle the thematic break, which the spec already lists as open (the "`$$` block" item, section 3), the same way. The records section stays outside the rule: it is a data section the plugin writes in a fixed place, and a closer written in a saved answer must not be able to hide it, nor to close a mark written in the body.

**C-069, a question asked for each pick, named alone in `from:`.** SPEC section 6 says such a follow-up "gives one row per pick and value" and notes that the reference renderer does not do this yet for `table`, `list` and `cards` (one row per entry, a field per pick) nor for `tiles`, `bars` and `line` (a line saying the view does not draw it yet). The plugin is ahead of the reference renderer here: all six views give one row per pick, in the source's order, its label the pick's words and its value the answer from the newest entry that answered it. The renderer should follow, and the spec should say what a row holds (label and value, and from which entry), which section 6 leaves open.
