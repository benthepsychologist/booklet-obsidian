# Lines proposed to the format spec (SPEC 0.18), from the plugin 1.0.0 choices review

This is a list, not an edit. Each entry says which choice row of `docs/choices-100.md` it comes from, what the plugin does, and the line the spec could say. Changing `SPEC.md` is its own piece of work in the Booklet repository.

Ben approved 18 rows for this list on 2026-11-03 ("yes to all 18 in Section 1"). Sixteen of them are here (the fifteen rows C-004 to C-068 named in the review, and C-002), with two spec sentences the review found. The other two of the 18 are C-033 (a structure line inside a comment) and C-069 (one row per pick); with a third entry, that the renderer should follow the format, they live in `docs/spec-proposals-e1.md`, which the code lane writes.

Every SPEC line number below was opened in `/workspace/booklet/SPEC.md` at its commit `ea964b0` (Format 0.18), on 2026-11-03. Where the spec already says part of a thing, the entry says so. The plugin code places are in each row of `docs/choices-100.md`; they were not re-opened for this list, except where an entry cites a `src/` line.

## From the 18 rows

**C-002. A host's own editor may change line endings and the byte-order mark.** When the note is also open in a Markdown pane, the plugin writes through that pane's editor, and Obsidian's editor saves LF endings and no byte-order mark. SPEC line 1159 says "A writer keeps the file's line endings, writes each line it adds with the file's own, and keeps a byte order mark." Proposed: add "unless the host hands the change to its own editor, which may change them; a writer that writes the file itself keeps them."

**C-004. A reader may clear any single-answer question.** The plugin clears a `choice` or a `scale` when the picked option is pressed again. SPEC line 537 allows clearing only for a matrix shown as separate questions ("may clear one by pressing its answer again, which stores `null`"); line 498 mentions "clear the pick and it goes" only about replies. I found no line allowing it for a `choice` or `scale`. Proposed: "A reader may clear the answer of a `choice` or `scale` by pressing the picked option again; the answer is then taken out of the record."

**C-005. The stored order of a `multi`.** The plugin stores picks in the order picked (`[3, 1]` if 3 came first) and shows replies and kept-entry words in the options' order. SPEC line 498 gives the replies' order (the options' order); line 612 says that a copy for each pick follows "the order the source's answer holds them (the order they were picked)", which assumes the stored order but section 5 never states it. Proposed, in section 5 under `multi`: "A `multi` stores its picks in the order the reader picked them."

**C-007. A blank line of a `lines` answer.** The plugin keeps every field of the live answer, blank ones included, as `""`, and leaves blank lines out of a kept entry. SPEC line 467 says only "`lines` is repeated one-line entries"; line 1130 says `[""]` holds nothing, which does not settle a list with some blank members. Proposed: "A `lines` answer lists every field in the draft, a blank one as an empty string; a kept entry leaves the blank lines out."

**C-009. An all-cleared matrix, and clearing in a grid.** The plugin keeps no answer for a matrix whose items are all cleared (the reference renderer keeps `[null, null]`), and lets the grid clear as well as the separate-questions layout. SPEC line 537 allows clearing only in the separate-questions layout; line 1130 defines "holding nothing" so that a list whose every member is `null` holds nothing and is no answer, which agrees with the plugin once read together. Proposed: say so in section 5 under `matrix` ("a matrix with every item cleared has no answer"), and say whether the grid may clear.

**C-010. Typed words with commas.** The plugin splits a reader's own words typed with commas at the commas, except where the whole text is a listed word's label that holds a comma ("Calm, settled"), or such a word already in the field. The words "comma" or "commas" appear in SPEC only in unrelated places (lines 98, 830, 1061). Proposed, in section 7 where the widget's own words are described: "Words typed with commas between them are several words, except where the whole text is the label of a word the widget lists."

**C-019. An own word equal to a listed word.** The plugin stores a word typed in a place's field as the listed word's id when it matches the label in any case, and otherwise as typed. SPEC line 1033 already says a typed word is one of the widget's words "when the two match in lower case", with quote and dash forms and white space read alike. The plugin's matching lowers case and reads the quote marks `’ ‘ \`` and `´` as `'` (`src/core/widgets.ts:30`); I did not check the dashes or white space. The part the spec leaves open is the stored form. Proposed: add to line 1033 that a typed word that matches is stored as that word's id.

**C-031. Where the reader is is not stored in the file.** The plugin keeps `{ version, screen, tab, page, part }` with the pane in Obsidian's workspace and never in the note. SPEC lines 197, 245, 272 and 345 each say that which state of a fold, tab, page or section is showing is "never stored" (line 272 for the page). Proposed, once in section 3: "Where the reader is (activity, tab, page, section, step) is never stored in the booklet file; a host may keep it with its own workspace."

**C-037. What Back does on a step.** The plugin takes a page with two or more groups one at a time; Back and Next move a step first, then a section, then a page, and Back from the first step goes where it went without steps. SPEC line 1285 describes the one-at-a-time view with "the pager's own Back and Next, and Next on the last step going on to the next `***` section"; lines 349 to 351 define Back and Next for sections and pages only. Proposed: "In the one-at-a-time view Back goes to the step before; on the first step it does what it does without steps."

**C-043. Which order Next follows.** The plugin's Next goes in the file's order of activities, not the module screen's tab-by-tab order (the two can differ). SPEC line 351 ends "goes on to the next activity" without saying in which order. Proposed: "Next at the end of an activity goes to the next activity in the file's order."

**C-044. "Exactly one activity" counts offered ones.** The plugin's start rule ignores a `hidden` activity, so a booklet with one offered and one hidden activity opens straight into the offered one. SPEC line 83 says a booklet that holds "exactly one activity" opens into it, and line 195 says `hidden` activities are "kept in the file, not offered". Proposed: "exactly one offered activity" in line 83.

**C-045. How a heading link is matched.** The plugin matches ignoring case, white space and Markdown marks, also against GitHub-style slugs, taking the first match in file order, and a link from another note looks through the whole file. SPEC lines 268 and 356 say a link "opens the first place ... whose heading or title reads those words", and give neither the matching rule nor the whole-file case. Proposed: add "words are compared ignoring case, white space and Markdown marks; a `#slug` form is matched against the slug of each heading; a link followed from another note looks through the whole file."

**C-056. How a matrix is summarised and drawn.** The plugin draws a matrix as buttons in both layouts; a query of one matrix question with `summary: on` gives a distribution for each item labelled "item · anchor"; an activity summary gives a row for each item, "title · item"; a kept entry shows "item: anchor's words" with a dash for an item not answered. SPEC line 959 says only "A matrix gives one row per item, each summarised like a scale", and line 961 does not mention a matrix. Proposed: state the row labels and the single-question distribution for a matrix, in section 6 under "Summaries".

**C-061. What a widget's colour names mean in a host with its own palette.** The plugin maps `warm` to Obsidian's red, `green`, `amber` to orange, `teal` to cyan and `slate` to the muted text colour on a wash of the text colour. SPEC line 1019 lists the names and says "The renderer draws the name in the active theme's colours", and line 864 ties `green`, `amber` and `warm` to the tones `good`, `warn` and `bad`. The plugin also draws `blue` as Obsidian's blue and `purple` as its purple (`styles.css:459`, `:460`, `:487` and `:491`). What the spec leaves open is whether a host may map a name to the nearest colour of its own palette. Proposed: "A host with its own palette may draw each colour name in the nearest colour of that palette."

**C-062. Questions inside any callout.** The plugin draws a question, a query view and a Booklet line inside any callout, not only a group; the reference renderer draws them only in a group. SPEC line 1310 records this as a known difference of the reference renderer ("the linter warns"). Proposed: either say in section 6 that a conforming reader reads them in any callout, or say which callout kinds hold them, so the difference is not only listed under the reference renderer's differences.

**C-068. A follow-up named alone in `from:` draws tiles, bars and a line.** The plugin draws them, one row per pick and value, in the source's order. SPEC line 889 already says "A follow-up named alone in `from:` gives one row per pick and value" and that the reference renderer does not do it yet. Proposed: no new rule; move the "does not do this yet" sentence out of the spec once the reference renderer follows (see `docs/spec-proposals-e1.md`).

## From the review's other findings

**The kept-entries fold mark `entries:folded` is read by the plugin.** SPEC line 1314 says "The Obsidian plugin does not read the mark yet; a reader that does not keeps it as written." The plugin reads it: `src/core/reader.ts:1034` to `1049` parses `entries:folded` on an activity line (any other value is reported and ignored), `src/core/reader.ts:314` and `315` hold it as `entriesFolded`, and `src/view.ts:1601` starts the list folded when it is set. Proposed: delete the sentence "The Obsidian plugin does not read the mark yet" from line 1314, or rewrite it as "The reference renderer and the Obsidian plugin both read the mark" once the reference renderer is checked.

**Remote pictures and a host's own renderer (C-083).** SPEC line 1273 says a conforming reader must "fetch no address a file names unasked (no remote image, ...)", and line 1275 says it must "request no remote image and no remote media from an origin the host or the reader has not allowed". Ben ruled on 2026-11-01 to "keep Obsidian's behaviour for images" (the row's source): the plugin draws a picture through Obsidian's own renderer and does not gate it, so a remote picture from an origin the booklet did not declare can be requested. The plugin and that sentence disagree. Proposed sentence, after the one on line 1275: "A host that hands pictures to its own renderer may leave a remote picture to that renderer, and then this paragraph's rule about pictures is the host's, not the reader's; the reader still requests no remote media of its own."
