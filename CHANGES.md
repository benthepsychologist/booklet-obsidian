# Changes

This file lists what changed in each release of the plugin. It did not exist before; it starts with an Unreleased section, and a release moves what is under it to a heading with its version (the version itself is set as `docs/release-flow.md` says).

## 1.6.0 (a beta)

1.5.0 was never released: everything that was to be in it ships here, listed under *From 1.5.0* at the end. The manifest, `package.json` and `versions.json` go from 1.4.0 to 1.6.0, and `versions.json` has no 1.5.0 line.

**The Design view.** A booklet note can now open in a third view beside the Booklet view and Markdown. It is a beta.

- **Three modes, and a setting.** Each of the three views has header buttons for the other two. The new setting **Open booklets in** (*Booklet view*, the default, or *Design view*) chooses the view a booklet note opens in at each opening; a person who never chooses it sees no change, and no key is added to `data.json` until a choice is made. A pane left in the Design view is restored after a restart. The view type is `booklet-design`. (`design-view.ts`, `switch.ts`, `settings.ts`.)
- **The tree.** The note drawn as the tree the format is: seven levels (booklet, module, module tab, activity, activity tab, page, block), each with its icon, indent, coloured rail, one line of words and a plain-words sentence on what it is, and a breadcrumb. Every line of the note belongs to exactly one node, so the tree reassembles the note byte for byte. Words go through Obsidian's renderer. A question of kind choice, multi, matrix, lines, text, number, scale or date, and a reading callout, is drawn as a reader sees it with nothing answered and every control switched off (nothing in a drawing can be pressed, and a drawing never shows or writes a reader's kept answer). Listen, widget and each questions, views and data blocks, the records, and text it cannot read are drawn as labelled cards with their Markdown as written: in this beta **listen, widget and each are cards, not drawings**. Media that points at another site is not drawn and nothing is fetched. (`core/design-tree.ts`, `design-model.ts`, `design-sample.ts`.)
- **Strict *+ Add*, and the catalogue.** *+ Add* lists only what the format allows in that place (each rule rests on a line of SPEC, and a refused place says why). It opens a catalogue in four folded groups (Structure, Questions, Reading aids, Views and data) and a group draws its live samples only when opened. (`core/design-places.ts`, `design-catalogue.ts`.)
- **Nested hotkeys.** A first letter (`s q r v d`) picks a group, a second a part, typing a word narrows the list, Enter adds the highlighted part, Escape closes. The keys are held in the view's own scope and never fire in a text field; every key action has a visible button; the palette commands (`design-add-piece` and `design-add-<group>`) have no default hotkey. (`core/design-keys.ts`.)
- **Move, delete, undo.** *Move up*, *Move down* and *Delete* on each block, each the smallest replacement of the note. A change that would leave kept answers, entries or rows not matching what they were kept for says how many and asks; it never blocks, and never deletes or rewrites the kept data. The view has its own *Undo* and *Redo* (buttons, Ctrl or Cmd with Z and Shift+Z while no field has the focus): a step is replayed only on the exact text it left behind, and is refused, with a reason, when the note was changed outside the view since. Writing goes into an open Markdown pane's editor, else `Vault.process`, the same path for the Booklet view. (`core/design-ops.ts`, `design-undo.ts`, `note-view.ts`.)
- **The form and the in-place editor.** A selected block shows its id, title, switches and fields as Obsidian's own setting rows; a change rewrites only its opening line, and a value the format would not read is refused with the reason. *Edit as Markdown* (or Enter) opens a small textarea for the block's own lines in the tree: Save (Ctrl or Cmd with Enter), Cancel, Escape keeps the changes as *Unsaved* and a second Escape throws them away; a note changed since it opened is refused as stale and the text is kept. (`core/design-form.ts`, `design-view.ts`.)
- **The outline and the lines the reader cannot read moved into the view,** with the kept data that matches nothing now. The *Booklet blocks* panel keeps *Add a block*, *This line*, *Options* and *Data fields*. (`core/design-outline.ts`; `editor-outline.ts` is gone.)
- **Spanish and French.** The Design view's own words (206 strings in `core/design-strings.ts`) are in Spanish and French when Obsidian is; English is the source and the fallback, and `.localize-state.json` holds the hash of each English string for the next `/localize` run. A counted word has `.one` and `.other`; French takes 0 and 1 as the singular. **Still English:** the names of the parts (the pieces' labels), the hotkey group names and their descriptions, some of the reasons a part cannot go somewhere or a change touches kept data, the words inside a drawn sample, a block's setting names, the palette command names, and the Booklet view and the editing panel, which are English only. Found and fixed with the real Obsidian in both languages: on a phone the confirm dialog's longer title ended in an ellipsis and its question mark ran under the close button; it now wraps and keeps clear of it.
- **A fix in the guard.** The data guard counted an activity's entries and drafts when the activity was deleted, but skipped the answers kept once for its questions (it did count them when the question alone was deleted). It now adds them, once per question id, and only where the id no longer stands in the module, so a renamed activity detaches none. (`core/editor-guard.ts`.)
- **Two defects found in the real Obsidian,** both fixed: a method named `dirty()` was shadowed by `TextFileView`'s own field of the same name, so opening the editor or deleting a block threw; and Obsidian's own default hotkey took Ctrl or Cmd with Enter before the editor's box could, so the view now holds that chord with a scope of its own while the box has the focus. The plugin's own buttons also beat Obsidian's button rule, which had left some of them cramped or overflowing.
- **Tests.** The Design view has its own tests in `test/design-*.test.mjs` and checks 64 to 71 of `e2e-tests/plugin-check.js` in the real Obsidian (the modes, the tree, the catalogue and keys, writes, the same writes with a Markdown pane, a phone's width, and Obsidian in Spanish and in French).

**From 1.5.0 (never released).**

- **The editing panel.** The command **Booklet: Editor mode** (`booklet:editor-mode`), and a button on the Booklet view, open a *Booklet blocks* panel beside the note: add a piece at the cursor, and change the settings of the line the cursor is on. It writes through the note's Markdown editor, so, like any edit made in Obsidian's editor, a change from the panel saves the note with LF line endings. Before a change that your readers' saved answers or rows depend on, it says how many it touches and asks; it refuses an id rename the linter calls an error and a click in a code block that never closes. The panel's view type is `booklet-blocks`. Its words are English only.
- **A data block written in the note is not written past 5 MB.** SPEC section 5 ("What stops it") says the data is left alone when the changed file would be larger than a reader reads (5 MB); for data written in the booklet, the changed file is the booklet itself, measured whole in bytes (UTF-8, a byte-order mark counted) after the change. The plugin applied that limit only to data files. An edit, an added row or a removed row that would make the note larger than 5 MB is now kept as an entry but not written into the block, and the notice says so: "change kept, but not written to the data block, because the booklet would be too big to read (the limit is 5 MB)", or, for a row, "the row was kept but not added to the data block. That would make the booklet too big to read (the limit is 5 MB), so it was not changed." A change that changes nothing is not held to it. (`core/apply.ts` `applyInFence`, `view.ts`.)
- **Test cases shared with the browser reader.** `test/apply-vectors.json` and `test/pending-vectors.json` are copies of the Booklet repository's files of the same names, made by running this plugin's core; `test/shared-row-cases.test.mjs` runs every case against the plugin. See the README, "Shared test cases". `test/lone-cr.test.mjs` pins that a carriage return alone ends no line (front matter included), as in the renderer.
